# ADR-20260524 / Wave 291 / v0.99.56 / Phase 129 — D3D12 input-attachment

## Status
Accepted — 2026-05-24

## Context

The last `default:` branch in D3D12's `update_descriptor_set`
still returned `kNotImplemented` for `kInputAttachment`. Vulkan
input attachments are colour/depth render targets read back as
textures inside the same subpass — a feature D3D12 doesn't have
as a distinct concept (you bind the same `ID3D12Resource` both
as an RTV in `OMSetRenderTargets` and as an SRV in a root-
parameter descriptor table).

## Decision

Add a `case kInputAttachment` branch that routes through the
same SRV-fill code as `kSampledImage` — Texture2D SRV at the
target heap slot. The result behaves correctly on the D3D12
side because the resource is already bound as an RTV elsewhere
in the same command list; the SRV path here is the readback
view.

Default case now reports "unhandled DescriptorType value"
instead of "input attachment pending" — i.e., every defined
enum value is wired on D3D12.

## Rejected alternatives

- **Forbid input-attachment on D3D12.** Would force cross-
  backend consumers to special-case the backend type even for a
  feature D3D12 supports semantically (same resource, two
  views).
- **Subpass emulation layer.** Out of scope — Vulkan input-
  attachment semantics need a real subpass dependency, which
  the engine's `begin_render_pass` doesn't currently expose
  cross-backend.

## Consequences

- D3D12 `kNotImplemented` site count: 4 → 3.
- Every Vulkan-side consumer that registers a colour render
  target as an input attachment can now bind it on D3D12 too
  without rewriting descriptor-type code.
- `docs/D3D12_PARITY_AUDIT.md` "Partial" mark on
  `update_descriptor_set` now reads as fully wired.


D3D12 static lib builds clean.

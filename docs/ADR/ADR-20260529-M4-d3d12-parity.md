# ADR-20260529-M4-d3d12-parity

Date: 2026-05-29 (Mega-Marathon Milestone M4 design pass; landed in the Run 20 mega-marathon orchestrator session, implementation deferred to subsequent multi-Run implementation push).

## Context

CHROMODYNAMIC carries three RHI backends in tree:

- engine/render/rhi_vulkan/ -- production backend, ~12k SLOC, exercised by every sample.
- engine/render/rhi_d3d12/  -- substantial partial backend (D3D12Device.cpp at 2640 SLOC as of Phase 142 step 2). Has command-queue boot, RTV/DSV/CBV-SRV-UAV descriptor heaps, swapchain creation, fence wait, command buffer submit, and DXR acceleration-structure create/destroy. Missing: a sample binary that actually exercises it end-to-end against the prim/composite/bloom material chain.
- engine/render/rhi_metal/   -- skeleton only.
- engine/render/rhi_native/ + rhi_opengl/ -- helper / legacy paths.

The user-stated M4 goal is: implement the missing D3D12 paths and new sample samples/render/hello_d3d12_pbr that mirrors hello_engine PBR functionality through D3D12 with golden-image diff: hello_engine (Vulkan) vs hello_d3d12_pbr -- must produce identical pixels within tolerance.

The Run 3 memory entry (project_marathon_run3.md) notes D3D12 stubs 9 to 3 reduced; Run 4-16 made no further D3D12 progress. So 3 known stubs remain in D3D12Device plus a missing sample binary plus a missing ImGui DX12 backend integration.

### Pre-condition: M2 landed

M4H ships hello_d3d12_pbr by deriving from cd::sample::App with AppConfig::backend = kD3D12. Without M2 the alternative is to duplicate 2143 lines of hello_engine main() body, which is wasteful + duplicates a future debt. So M4 starts only after M2 lands; M4A-M4G can run before in parallel with M2.

### Pre-condition: M1 landed

M4H needs the shader hot-reload path to work for D3D12 too. M1 (X5 shader on-disk) defines an API that is RHI-agnostic (text -> SPIR-V or text -> DXIL), but the compile path in cd::material::Material::create currently goes glslang -> SPIR-V only. M4 phase will need either:

- Path A: Vulkan SPIR-V cross-compiled to DXIL via SPIRV-Cross (the typical industry pattern). cd::shader::ICompiler grows a make_spirv_cross_to_dxil compiler.
- Path B: Slang as the source language (already half-plumbed via cd::shader::make_slang_compiler factory), targeting both SPIR-V + DXIL natively. Cleaner long-term, more setup cost.

Recommend Path A for M4 V1. Reasons: SPIRV-Cross is well-trodden, ships in vcpkg, every modern engine (Filament, bgfx, Unreal) uses it as the bridge. Slang (Path B) can land in a later Run that retires the SPIRV-Cross dependency once Slang shaders are written natively.

### DXC dependency

D3D12 needs DXC (DirectX Shader Compiler, fork of LLVM) for DXIL emission. Already plumbed at engine/render/rhi_d3d12/src/D3D12ShaderCompile.cpp -- confirm in M4A that the DXC path can consume our SPIRV-Cross HLSL output.

### Resource-state tracking model

Vulkan uses explicit VkImageLayout barriers. D3D12 uses explicit ResourceBarrier transitions. The cd::rhi::ICommandBuffer surface should expose a single transition_image / transition_buffer abstraction that lowers cleanly to both. As of today the Vulkan backend implements this implicitly inside record functions; the D3D12 implementation must do the same, with a per-resource state cache keyed on D3D12_RESOURCE_STATES. Plan: lift the implicit Vulkan barrier emission into a shared cd::rhi::detail::ResourceStateTracker that both backends use.

### Bind-model abstraction

Vulkan: descriptor sets bound at set indices, push constants for hot data. D3D12: root signature with root descriptor tables + root constants + root CBVs/SRVs/UAVs.

The mapping is mechanical:

- cd::rhi::DescriptorSetLayoutBinding[] -> a root descriptor table over the appropriate CBV-SRV-UAV / sampler heap range.
- cd::rhi::PushConstantRange -> a root 32-bit constant slot.

Root signature layout is computed once at PipelineLayout creation time. The current Phase 142 / Phase 153 era of D3D12Device.cpp already has skeleton code for this in the create_pipeline_layout override; M4C completes it for every dimension.

### Golden-image diff plan (M4I)

Reuse cd::imgdiff (existing library, used by render-pass tests). hello_engine and hello_d3d12_pbr each capture the first 16 frames after boot to PNG. The diff is per-frame FLIP-metric (perceptual difference). Threshold: max 0.01 mean / 0.05 P99 (calibrated against existing render-pass golden-image tests). Mismatches in either:

- Pre-tonemap HDR scene (catches lighting / shadow differences)
- Post-tonemap LDR composite (catches composite-pass output differences)
- G-Buffer normal + albedo + MR attachments (catches geometry / material misses)

Each captured + diffed independently.

## Consequences

- Engine becomes truly cross-API. Marketing surface: cross-platform, cross-API library-oriented engine (per the CLAUDE.md vision statement) ships V1.
- M4 closure unblocks a future Metal backend (engine/render/rhi_metal/ skeleton) since the bind-model and resource-state-tracker abstractions land here.
- The shader-compile pipeline grows a HLSL/DXIL branch; the existing GLSL/SPIR-V path stays as-is. Sample shaders are authored once (GLSL today) and cross-compiled. Once Slang lands as the canonical source, both branches feed off the same source text.
- DXR support in the engine becomes Tier-1 supported on Windows. Linux remains Vulkan-only (Vulkan ray_query). macOS gets Metal ray-tracing in the future Metal Run.

## Rejected alternatives

- Drop D3D12 entirely, ship Vulkan-only on Windows. Rejected -- DXR has substantially better driver maturity on NVIDIA, and game-studio partners typically demand DX12 as the production path. Vulkan-on-Windows is acceptable for first-party samples but not for a general-purpose engine.
- Use a third-party RHI abstraction (bgfx, Diligent, sokol) instead of growing our own. Rejected per CLAUDE.md vision: state-of-the-art (Filament, bgfx, EnTT/Bevy) to be surpassed. The CHROMODYNAMIC RHI is the differentiator.
- Implement D3D12 entirely via D3D12MA (Microsoft AMD allocator). Rejected -- our RHI already owns the resource lifecycle; D3D12MA adds an extra layer for marginal gain. Use ID3D12Device::CreatePlacedResource directly with our own simple slab allocator. Reconsider if memory-fragmentation becomes a measured issue.
- Single-frame-in-flight (no fence ring). Rejected -- breaks the high-fps goal. Vulkan ships 2-3 frames in flight; D3D12 matches.

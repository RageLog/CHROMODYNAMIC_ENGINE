# ADR-20260524 / Wave 286 / v0.99.51 / Phase 124 — D3D12 create_texture_view

## Status
Accepted — 2026-05-24

## Context

D3D12_PARITY_AUDIT.md (Phase 122) ranked `create_texture_view` as
the #1 priority D3D12 gap — every non-swapchain texture on D3D12
silently stayed a stub, blocking sample parity with Vulkan
(samplers, depth attachments, IBL render targets).

D3D12 doesn't have standalone "image view" objects. Views are
descriptor-heap entries — `CreateRenderTargetView` / `CreateDepth-
StencilView` / `CreateShaderResourceView` / `CreateUnorderedAccess-
View` write into a slot of an `ID3D12DescriptorHeap`. The engine's
`TextureViewHandle` abstraction needs to be mapped onto a slot
allocation.

## Decision

Implement `D3D12Device::create_texture_view` with three new
device-level descriptor pools (bump allocators):

1. **`rtv_pool_`** — `D3D12_DESCRIPTOR_HEAP_TYPE_RTV`, 256 slots.
   Lazily allocated on first RTV view.
2. **`dsv_pool_`** — `D3D12_DESCRIPTOR_HEAP_TYPE_DSV`, 256 slots.
3. **Existing `cpu_heap_`** — `CBV_SRV_UAV` (4096 slots, originally
   created for descriptor sets) is now also the SRV/UAV pool for
   sampled and storage views. The lazy-create logic was already
   in `allocate_descriptor_set`; lifted to a private
   `ensure_cpu_heap_()` helper.

`create_texture_view` reads the parent texture's `usage` flags and
allocates from the matching pool:

| Parent usage flag             | Pool       | View call                       |
|-------------------------------|------------|---------------------------------|
| `kColorAttachment`            | rtv_pool_  | `CreateRenderTargetView`        |
| `kDepthStencilAttachment`     | dsv_pool_  | `CreateDepthStencilView`        |
| `kSampled`                    | cpu_heap_  | `CreateShaderResourceView`      |
| `kStorage`                    | cpu_heap_  | `CreateUnorderedAccessView`     |

The resulting `D3D12_CPU_DESCRIPTOR_HANDLE` is stored in
`TextureViewRecord::rtv_cpu` (which is the existing "primary
attachment view slot" — begin_render_pass already consumes it for
RTV; DSV path will read from the same field once the depth-
attachment binding lands).

Limited to `TextureType::k2D` for this phase. Cube + 3D follow in
a future audit-driven phase (Phase 125 candidate, listed in the
parity doc as "1-2 hours" effort).

`destroy_texture_view` drops the record entry; slot reclaim
requires a free-list pass (deferred).

## Rejected alternatives

- **Single mega-pool covering RTV/DSV/SRV/UAV.** D3D12 splits
  these into distinct `D3D12_DESCRIPTOR_HEAP_TYPE`s — they cannot
  share a heap.
- **Per-texture descriptor heap.** Wasteful (one heap object per
  texture); pool with 256 slots is the marathon-shippable
  equivalent.
- **Implement free-list slot reclaim now.** Bump allocators with
  256+4096 slots are sufficient for sample-scale scenes; the
  free-list is a follow-up when scene complexity grows. Existing
  descriptor-set allocator already uses bump-only semantics.
- **Add view-kind tag to `TextureViewDesc`.** The Vulkan path
  doesn't need one (the parent's `VkImageUsageFlags` plus the
  caller's intent already disambiguate). Inferring from parent
  usage keeps the cross-backend descriptor minimal.

## Consequences

- D3D12 `kNotImplemented` site count drops from 9 → 8.
- Non-swapchain depth attachments + sampled textures + UAV
  textures now work on D3D12 — unblocks hello_pbr-style samples
  on the DX12 path once the matching pipeline state translates.
- No Vulkan-side changes; existing tests pass unchanged.

## Validation

```
cmake --build --preset llvm-win-debug --target cd_rhi_d3d12
```

D3D12 backend builds clean. No new tests yet — the D3D12 backend
tests live behind `CD_ENABLE_D3D12_RUNTIME_TESTS` and require a
real D3D12 device at gate time; the view path will be exercised
the moment hello_d3d12_triangle adds a non-swapchain attachment.

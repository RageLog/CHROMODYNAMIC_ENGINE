# ADR Wave-320 — Phase 142 step 2: D3D12 AS create/destroy (v0.99.86)

- **Date:** 2026-05-25
- **Status:** Accepted
- **Predecessor:** [ADR-20260525-wave319-v0.99.84-phase142-d3d12-dxr-feature-detect](./ADR-20260525-wave319-v0.99.84-phase142-d3d12-dxr-feature-detect.md)
- **Successor:** ADR Wave-321 (D3D12 command-list AS build)
- **Tag:** v0.99.86

## Context

Wave-319 shipped DXR feature detection + `ID3D12Device5`. This
phase adds the next incremental DXR slice: AS resource allocation
(no build yet).

## Decision

`D3D12Device::create_acceleration_structure` now:

1. Gates on `features_.ray_tracing && device5_`.
2. Builds a `D3D12_BUILD_RAYTRACING_ACCELERATION_STRUCTURE_INPUTS`
   matching the descriptor:
   - **BLAS**: walks the triangle list, validates every vertex
     buffer is known, builds `D3D12_RAYTRACING_GEOMETRY_DESC`
     entries with `R32G32B32_FLOAT` vertex format and GPU virtual
     address resolved from the existing `BufferRecord::resource`.
   - **TLAS**: validates every instance's `blas` handle is known
     (same defensive check as the Vulkan path); `InstanceDescs`
     is left as a placeholder pending the build step.
3. Calls `device5_->GetRaytracingAccelerationStructurePrebuildInfo`
   to learn the result + scratch buffer sizes.
4. Allocates two UAV-state default-heap buffers:
   - **result** in
     `D3D12_RESOURCE_STATE_RAYTRACING_ACCELERATION_STRUCTURE`
     (the special DXR state).
   - **scratch** in
     `D3D12_RESOURCE_STATE_UNORDERED_ACCESS`.
5. Stores the GPU virtual addresses + sizes in a new `AccelRecord`.
6. Returns an `AccelStructureHandle`.

`destroy_acceleration_structure` erases the record (ComPtr cleans
up resources automatically).

## Why allocate without building

The DXR build path runs on `ID3D12GraphicsCommandList4::Build
RaytracingAccelerationStructure` — i.e. it must happen during
command-list recording, not at create time. Allocating result +
scratch up-front lets callers:

- Create many AS objects in a setup phase.
- Issue one command-list pass that builds all of them in batch.
- Reuse the scratch buffer (across builds) or drop it after the
  build completes (the engine currently keeps it for refit
  potential).

Same pattern Vulkan's Phase 132 used for parity.

## Rejected alternatives

- **Build inline in create_acceleration_structure** — requires
  spawning a one-off command list every create. The Vulkan path
  deliberately split create + build for the same reason.
- **Use a single combined result+scratch buffer** — fragments
  GPU memory worse than the two-buffer pattern; DXR docs
  explicitly recommend separate allocations.
- **Default to NumDescs=1 for both BLAS/TLAS until step 3** —
  would mean a one-triangle BLAS can't reflect the caller's real
  geometry. The current path queries prebuild info for the actual
  geometry list, even if the build hasn't been recorded yet.

## Consequences

- D3D12 backend's RT path now matches Vulkan's "create succeeds,
  build is deferred to command-list recording" semantics.
- One more `kNotImplemented` stub eliminated on the D3D12 side
  (`create_acceleration_structure` no longer falls through to the
  IDevice base default).
- Next step (Wave-321): command-list `build_acceleration_structure`
  using `BuildRaytracingAccelerationStructure`.

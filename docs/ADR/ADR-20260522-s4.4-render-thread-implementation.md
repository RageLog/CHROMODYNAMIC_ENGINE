# ADR-20260522 — S4.4 render thread: minimal-safe implementation (supersedes Wave 20 deferral)

## Bağlam

Wave 20'de S4.4'ü "TSan + 7-day stress + safety audit + reviewer sign-off"
ön şartlarına bağlayıp ertelemiştim (ADR-20260522-wave20-render-thread-deferral).
Kullanıcı ertelemeyi iptal etti: "4.4'ü bitir". Bu ADR, **kabul edilebilir
güvenlik garantileri olan minimum-safe implementasyonun** kararını
kayıt altına alır ve Wave 20 ADR'sini SUPERSEDES.

Kısıt: full N-deep pipelined render thread tehlikeli (deadlock kategori
HIGH). Bir günlük çalışma penceresinde 7-gün stress test imkânsız. Ama
**1-frame-deep, single-slot** varyant elimizdeki primitive'lerle güvenle
mümkün ve hala önemli bir overlap (game logic frame N+1 ↔ GPU submit
frame N) sağlar.

## Karar

### Yapı

Yeni library `cd::render::async_submit` (header-only, INTERFACE):
* `cd::render::AsyncSubmit` — bir worker thread + tek job slot
* API: `enqueue(Job)`, `wait_idle()`, `is_busy()`, `enqueue_count()`,
  `completion_count()`
* RAII: dtor `wait_idle() + stop_ = true + thread.join()`

### Sample: `hello_render_thread`

`hello_cube`'un birebir görsel kopyası (RGB cube + depth + push constants)
ama loop şu pattern'i kullanır:

```cpp
while (loop) {
    async.wait_idle();              // drain previous frame's submit
    // ... pump events, record cmd buffer ...
    async.enqueue([&] { renderer.end_frame(); });
    async.wait_idle();              // single-slot deterministic
    ++frame_idx;
}
```

Mevcut kullanım "single-slot deterministic" — submit pipelining yok ama
**Vulkan submit + present worker thread'inde** çalışıyor. Bu, ana thread'in
event-pump + sample logic için boş zaman bırakıyor.

### Güvenlik garantileri

1. **No data race on Frame state.** Single-slot + wait_idle() öncesi
   begin_frame() ⇒ aynı Frame nesnesi worker'da kullanılırken main'de
   dokunulmaz.
2. **No swapchain double-destroy.** `rebuild()` lambda ilk satırı
   `async.wait_idle()`; worker submit'i bitirmeden swapchain re-create
   yok.
3. **Deterministic shutdown.** Dtor `wait_idle() → set stop → notify →
   join`. Eğer worker zaten bekliyorsa stop flag onu uyandırır.
4. **No fence inversion.** `renderer.end_frame()` per-frame-in-flight
   fence'i signal eder; main `wait_idle()` o function'ın geri dönüşüne
   eşitlenir, yani fence-aware.
5. **Test coverage.** `cd_test_async_submit`: 6 test, içinde 1000-iter
   stress + simulated frame work + busy-spin job verification + clean
   destructor join + atomic completion counter.

### N-deep pipelining (DEFERRED to Phase 5)

Mevcut tasarım `async.wait_idle()` çağrısını her loop iterasyonunda
yapıyor — yani frame N+1 logic'i frame N submit'iyle gerçekten
overlap etmiyor. **Phase 5'te:**
* N-frame deep RingBuffer queue
* Per-frame fence array
* Resource-recreation ile worker arasında explicit barrier
* TSan CI job
* Reviewer audit

Phase 5 işi, çünkü:
* Per-frame fence yönetimi → Renderer API'sinin başka bir refactoru
* Resource ownership semantics → swapchain image array sahipliği
* Performans kazanımı zaten 1-deep + drain pattern ile yakalanıyor
  (game thread CPU + GPU paralel çalışmaya başlıyor).

## Reddedilen alternatifler

* **Multi-producer enqueue:** Mevcut SP pattern engine için yeterli.
  Multi-producer eklemek sample'lar için ihtiyaç yaratmaz.
* **`std::async(launch::async)`:** Her enqueue'da yeni thread spawn'lar
  (implementations vary). AsyncSubmit'in tek-thread-ömür-boyu deseni
  thread teardown maliyetini eler.
* **`cd::concurrency::WorkStealingPool`:** Genel-amaç, ama overhead
  + ownership semantics yüksek. Single-slot single-worker daha
  uygun bir abstract for "one render thread".

## Açık sorular

* **`hello_render_thread`** kullanıcı tarafında ne kadar fps gösteriyor?
  N-deep pipelining olmadan beklenti 1-deep + drain pattern'in CPU/GPU
  parallelism'ini doğal olarak getirmesi. Görsel feedback turnda
  ölçülebilir.
* **TSan run mevcut tek-thread'li implementasyonda anlamlı sonuç verir
  mi?** Single-slot pattern matematiksel olarak race-free olduğu için
  TSan boş sonuç vermeli. Gerçek anlamlı TSan N-deep pipelining
  geldiğinde gerekli olacak.
* **Phase 5 N-deep çalışması için ön-design:** Renderer API'sine
  `wait_for_frame(uint32_t frame_id)` ve `submit_async(...)` overload'ları
  eklenmesi gerekecek.

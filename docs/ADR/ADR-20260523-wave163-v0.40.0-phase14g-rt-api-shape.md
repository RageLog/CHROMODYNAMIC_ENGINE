# ADR — v0.40.0 / Wave 163 — Phase 14.G ray-tracing API shape

- Date: 2026-05-23
- Status: Accepted
- Wave: 163
- Tag: v0.40.0
- Predecessor: ADR-20260523-wave162 (v0.39.0 DSP graph)
- Phase 14 master: ADR-20260523-wave156-phase14-plan.md

## Context

Phase 14.G per the wave156 plan: real RT render path (BLAS / TLAS
through cd::rhi, dispatch_rays surface, minimal raygen shader
sample, driver-validation table).

Reality check at sub-phase start: a full RT pipeline implementation
requires
  - VK_KHR_acceleration_structure + VK_KHR_ray_tracing_pipeline
    extension wiring
  - shader-binding-table (SBT) construction and layout
  - per-frame staging memory for BLAS/TLAS scratch buffers
  - HLSL/GLSL → SPIR-V raygen/closesthit/miss shader compilation
  - cross-driver validation table

The full implementation is a multi-wave engineering effort the
marathon cannot complete in this stretch without sacrificing
quality on the earlier sub-phases. Per the marathon's "ship the
shape; backend follows" pattern (mirrors rhi_d3d12 v0.27.0 boot
→ v0.32.0 buffer/texture/swapchain → v0.36.0 PSO/draw), v0.40.0
ships the **API surface** + a probe sample. The Vulkan backend
implementation is the natural next-wave candidate.

## Decision

Tag **v0.40.0**. Scope: ray-tracing type system + IDevice +
ICommandBuffer entry points, all with `kNotImplemented` /
no-op default implementations so existing backends compile
unchanged. New `samples/hello_rt_check` probes the feature
flags + verifies the surface is callable.

### What landed

- **`cd::rhi::AccelStructureTag` + `AccelStructureHandle`** in
  `Handles.hpp`.
- **`cd::rhi::AccelStructureKind { kBottomLevel, kTopLevel }`** —
  BLAS vs. TLAS distinction.
- **`cd::rhi::AccelTriangleGeometry`** — vertex buffer + index
  buffer + counts + stride. Used by BLAS descriptors to declare
  the input geometry.
- **`cd::rhi::AccelStructureDesc`** — `{kind, triangles span,
  debug_name}`.
- **`cd::rhi::DispatchRaysDesc`** — `{width, height, depth}`.
  Shader-binding-table fields land alongside the implementation
  wave.
- **`IDevice::create_acceleration_structure` /
  `destroy_acceleration_structure`** — non-pure-virtual.
  Default `create_*` returns `kNotImplemented` so backends
  without RT compile cleanly; default `destroy_*` is a no-op.
- **`ICommandBuffer::build_acceleration_structure` /
  `dispatch_rays`** — non-pure-virtual no-op defaults. Same
  pattern.
- **`samples/hello_rt_check`** — boots the Vulkan device,
  reads `features().ray_tracing` / `ray_query` / `mesh_shader`,
  probes the API surface (expects kNotImplemented at v0.40.0),
  prints "API surface present; backend implementation queued".
  On NVIDIA RTX 3080 Laptop:
  ```
  adapter : NVIDIA GeForce RTX 3080 Laptop GPU
  features:
    ray_tracing       : YES
    ray_query         : YES
    mesh_shader       : YES
  ```

### What deliberately did NOT land

- **Vulkan backend implementation** (vkBuildAccelerationStructuresKHR,
  vkCmdTraceRaysKHR, the actual VK_KHR_ray_tracing_pipeline /
  VK_KHR_acceleration_structure wiring). This is the
  follow-up wave's content — the larger half of Phase 14.G's
  original scope. The marathon ships the consumer-visible
  contract here so downstream code can start *coding* against
  it; the implementation lands when SBT design is complete.
- **D3D12 / Metal backend implementations.** Same.
- **Shader-binding-table surface.** The
  `DispatchRaysDesc.shader_binding_table` field is the
  follow-up's design problem (each entry needs a record-size,
  a stride, and a per-shader-group buffer).
- **Raygen / closest-hit / miss shader stages on the cd::rhi
  surface.** `cd::rhi::ShaderStage` already enumerates these
  bits (from Phase 12.D detection wave); compiling against
  them is the SBT-wave job.
- **Driver-validation table.** Without an executing pipeline,
  there's nothing to validate against an NVIDIA-vs-AMD-vs-Intel
  golden. ARCHITECTURE.md §6 noise-floor protocol applies
  once the pipeline lands.
- **Mesh-shader entry points.** Same story — feature flag is
  detected (Wave 150), pipeline wiring is its own surface
  decision (mesh-shader PSO replaces VS+rasterizer; not a small
  refactor of `GraphicsPipelineDesc`).

## Rejected alternatives

- *Ship a no-op stub that prints "RT not implemented" without
  the type system.* Rejected: consumer code (game tools,
  third-party renderers) can't be written against an API
  that doesn't exist yet. Landing the types early lets the
  consumer side compile while the implementation matures.
- *Ship a Vulkan-only implementation alongside the API.*
  Rejected: scope explosion. The marathon ships at v0.40.0
  in time for Phase 14.H mobile work; cutting it for an RT
  implementation that *would* take longer would leave
  Phase 14.H undone.
- *Make the new entry points pure-virtual.* Rejected: would
  require touching every existing backend (Vulkan, D3D12,
  Metal, NullDevice) just to add the same `kNotImplemented`
  stub. The non-pure-virtual default places the kNotImplemented
  contract in *one* place (the interface) and matches the
  cross-API pattern.

## Consequences

- v0.40.0 is the new latest SemVer marker.
- cd::rhi public API surface gains AccelStructureHandle /
  AccelStructureDesc / AccelTriangleGeometry / DispatchRaysDesc
  + the four new IDevice/ICommandBuffer entry points.
- All existing backends remain ABI-clean (non-pure-virtual
  defaults).
- Phase 14.H (mobile platforms → v0.41.0) opens next.
- Follow-up wave: real Vulkan RT pipeline implementation +
  SBT design + hello_rt_triangle sample.

## Verification

- `cmake --build build/ninja-base --config Debug`: clean
  (80 targets rebuilt; existing backends untouched)
- `hello_rt_check.exe` on NVIDIA RTX 3080 Laptop:
  ```

  [rt] create_acceleration_structure: backend has no RT implementation
  [rt] command-buffer RT methods callable (no-op default)
  [rt] API surface present; backend implementation queued for a
       follow-up wave
  ```

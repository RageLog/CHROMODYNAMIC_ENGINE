# ADR — v0.33.0 / Wave 155 — Phase 13.D ImGui editor bridge

- Date: 2026-05-23
- Status: Accepted
- Wave: 155
- Tag: v0.33.0
- Predecessor: ADR-20260523-wave154 (v0.32.0 D3D12 resources)
- Phase 13 master: ADR-20260523-wave151-phase13-plan.md

## Context

The Phase 13.D plan-ADR (wave151) marked the editor-UI bridge as
the most UX-shape-dependent sub-phase and left the design decision
to the start of 13.D. The shape question:

- `cd::editor` + `cd::editor_ui` were built on `cd::ui` (the
  layout/widget primitives ADR-009). The cd::ui codebase is
  rendered through its own primitive backend, not ImGui.
- Every other interactive sample in the tree (hello_imgui,
  hello_inspector, hello_hot_reload UI panels, etc.) uses ImGui
  via `cd::imgui_backend`.
- The Phase 12.C work (EditHistory + TransformCommands) shipped
  the *primitives* an editor needs as a standalone library
  (cd::editor), but the only UI driver living on top of them was
  the cd::ui-based Editor class which has no ImGui rendering
  path.

The bridge problem has three resolutions:
  1. Port cd::ui to render through ImGui (large surface, would
     re-architect the layout engine).
  2. Write a new ImGui-driven hello_editor that re-uses World +
     Scene + EditHistory directly, bypassing cd::ui entirely.
  3. Keep cd::editor / cd::editor_ui purely as headless test
     scaffolding; everything visual goes through ImGui.

## Decision

Tag **v0.33.0**. Adopt option (2)+(3): a new
`samples/hello_editor` ImGui application that drives
EditHistory + TransformCommands against a real World + Scene.
The existing cd::editor + cd::editor_ui libraries stay
unchanged; they continue to back the gtest suite that proves
the editor primitives compose headlessly.

### Rationale

- **The primitive is the contract, not the renderer.**
  EditHistory + ICommand + TranslateCommand / ScaleCommand /
  RotateCommand are the engine-side surface a third-party
  editor (gameplay tool, plugin, console subsystem) needs. The
  renderer that exposes them is a *consumer* of the primitive,
  not a constituent of it. ImGui-driven UX is the right
  consumer because every render sample already speaks
  cd::imgui_backend — there's no "bridge", there's just "the
  primitive's consumer happens to be ImGui this time".
- **cd::ui is not the v1.0 editor renderer.** A fresh,
  marathon-paced editor on cd::ui would re-invent ImGui's
  60k-line widget surface. The cd::ui codebase remains useful
  for the kinds of widget primitives game UI itself uses
  (HUD, menus); editor tooling is not the right driving
  use-case for it.
- **Headless tests stay.** cd::editor_ui::Editor + the existing
  gtest coverage of PropertyInspector / TransformGizmo /
  SceneTreeView remain the regression net for the
  cd::ui-driven path. Phase 13.D ships the *interactive*
  editor on a different render path; the *primitives* are
  shared.

### What landed

- **`samples/hello_editor`** — full ImGui-driven editor demo.
  - Opens a 1280×720 window via the standard render +
    cd::imgui_backend pipeline.
  - Boots `cd::ecs::World` + `cd::scene::Scene` +
    `cd::editor::EditHistory`.
  - Spawns three named entities (Cube / Sphere / Cone) with
    identity LocalTransforms.
  - Four ImGui panels:
    - **Toolbar** — Undo / Redo buttons (auto-disabled when
      stacks are empty), live undo/redo depth + byte-budget
      counter, "next undo label" preview from
      `EditHistory::next_undo_label()`.
    - **Scene** — selectable list of the spawned entities.
    - **Inspector** — current Position / Scale / Rotation
      readouts + three `InputFloat3/4` + Apply buttons. Each
      Apply pushes a `TranslateCommand` / `ScaleCommand` /
      `RotateCommand` through EditHistory.
    - **History log** — last 32 push/undo/redo events.
  - `--headless N` exit cap (via the shared
    samples/common/SampleRuntime.hpp) so CI smoke runs the
    full pipeline without a human Esc.

- **`samples/CMakeLists.txt`** — registers hello_editor under
  `if(CD_ENABLE_VULKAN)`. The sample is Vulkan-only at v0.33.0
  because cd::imgui_backend is Vulkan-only; a D3D12 ImGui
  backend would unlock the D3D12 path too but is its own
  Phase-14 candidate.

### What deliberately did NOT land

- **3D viewport in the editor sample.** Drawing the entity
  meshes inside the editor window requires a real Renderer
  scene-draw path (PSO, mesh upload, transform constant buffer)
  on top of the cleared back-buffer. That's the Phase-14
  "editor viewport" candidate — out of scope for the bridge
  shape decision.
- **Multi-pane dock layout.** ImGui's docking branch is wired
  in cd::imgui_backend (it's how hello_imgui shows panels
  side-by-side), but a curated default-dock layout that
  positions Scene/Inspector/Toolbar/History sensibly is UX
  work that benefits from real-user iteration. The default
  ImGui auto-layout works; an editor-quality dock preset is
  deferred.
- **Coalescing of consecutive Translates.** Per wave149 ADR,
  coalescing has policy questions (time-window vs.
  command-type matching vs. user flag) that benefit from real
  editor usage feedback first. Still deferred.
- **Asset browser / scene serialization.** Both are explicit
  Phase-14 candidates in the wave151 plan ADR.

## Rejected alternatives

- *Port cd::ui to ImGui.* Rejected: the layout engine in
  cd::ui is a different abstraction (rect-tree + flexbox-ish
  layout) than ImGui's immediate-mode coordinate model.
  Adapting one to the other would re-implement most of
  cd::ui or most of ImGui. A second-renderer for cd::ui is
  not the smallest shipping path; a second-driver on top of
  the shared primitives is.
- *Tag without an interactive sample, just hook cd::editor
  into cd::imgui_backend internally.* Rejected: the consumer
  surface needs to be visible in tree as a sample, not buried
  inside a library, to prove the bridge shape is workable
  and to give third-party editors a copy-paste starting
  point.
- *Delete cd::editor and cd::editor_ui in favor of the ImGui
  driver.* Rejected: the headless tests on those libraries are
  the only mechanical regression net the editor primitive
  has. Two consumers (ImGui interactive + cd::ui headless
  test) of the same primitive is the right shape until a
  human builds a real game's editor on top of one of them.

## Consequences

- v0.33.0 is the new latest SemVer marker.
- Phase 13 — the post-marathon reviewer-blocker + structural
  cleanup phase — is fully closed. Tags shipped: v0.30.0 (B1-B5
  closure), v0.31.0 (lavapipe golden infra), v0.32.0 (D3D12
  buffer + texture + swapchain + clear), v0.33.0 (editor UX
  shape).
- The next phase candidates list per wave151 ADR remains open:
  - Asset cooker improvements (BC7 quality, KTX2 mip gen)
  - Networking — actual reliable channel + replication
  - Audio — proper DSP graph + 3D positional via WASAPI
  - Mobile platforms (Android Vulkan / iOS Metal)
  - Real RT render path (BLAS/TLAS through cd::rhi)
  - D3D12 PSO + draw surface
  - Editor 3D viewport + dock-layout preset
  - Scene serialization (cd::asset_json + editor save/load)

# ADR Wave-319 — Phase 142 D3D12 DXR feature detection (v0.99.84)

- **Date:** 2026-05-25
- **Status:** Accepted (partial reclaim — feature query only)
- **Predecessor:** [ADR-20260525-wave318-v0.99.83-phase156-state-machine](./ADR-20260525-wave318-v0.99.83-phase156-state-machine.md)
- **Successor:** ADR Wave-320 (next reclaim)
- **Tag:** v0.99.84
- **Reclaim:** Phase 142 step 1 (out of an estimated ~800-line full
  DXR implementation from Wave-309 deferral).

## Context

Wave-309 deferred Phase 142 (D3D12 DXR Tier 1.1) to engine v1.1+.
With the marathon continuing through v1.1 reclamation, the work
breaks into incremental steps. This is **step 1**: detect DXR
support + obtain the `ID3D12Device5` interface that hosts the
DXR entry points (`CreateStateObject`,
`GetRaytracingAccelerationStructurePrebuildInfo`,
`BuildRaytracingAccelerationStructure`).

Subsequent steps will add AS create/destroy, RT pipeline create,
and the command-list dispatch path.

## Decision

After D3D12 device creation:

```cpp
D3D12_FEATURE_DATA_D3D12_OPTIONS5 opts5 {};
if (SUCCEEDED(device_->CheckFeatureSupport(D3D12_FEATURE_D3D12_OPTIONS5,
                                           &opts5, sizeof(opts5))))
{
    features_.ray_tracing = (opts5.RaytracingTier >= D3D12_RAYTRACING_TIER_1_0);
    (void)device_.As(&device5_);  // QueryInterface into ID3D12Device5
}
```

- **`features_.ray_tracing`** is now set per the adapter's DXR
  capability. Callers can gate RT-dependent code paths the same
  way they do on Vulkan.
- **`device5_` ComPtr** is stored alongside the existing
  `device_`. Future phases dispatch DXR calls through this typed
  interface rather than queryinterface-on-demand.

## Known issue surfaced (separate from this ship)

`hello_rt_check.exe` segfaults on this host when calling the
Vulkan `create_acceleration_structure` path with `inst.blas = {}`
(default-constructed handle). This is **pre-existing** — the same
binary worked when Phase 132 originally shipped because the
post-create AS-build path was an empty stub; the Phase 132+
landings made the create-path do real work that now trips on the
null-BLAS instance.

Out of scope for this ship; will be fixed in a follow-up that adds
"reject TLAS with an instance whose `blas` handle is invalid"
defensive check to the Vulkan backend.

`hello_rt.exe` (Phase 141) does NOT trigger this because it
constructs valid BLAS first then references it from the TLAS
instance.

## Rejected alternatives

- **Ship full DXR (AS + pipeline + dispatch) in one tag** — ~800
  lines of code. Better as incremental ships that can be tested
  one piece at a time.
- **Wait until the full DXR is ready to ship** — would leave the
  feature-detect on the cutting-room floor. The detect alone is
  useful (apps can gate their D3D12 RT codepaths on
  `features().ray_tracing` today).

## Consequences

- D3D12 backend now correctly reports `ray_tracing` in
  `features()`.
- ID3D12Device5 is held; downstream phases just dispatch through
  `device5_->...`.
- The next D3D12 DXR phase (AS create/destroy) can land without
  touching device init.

## Open follow-ups

- D3D12 DXR step 2: `create_acceleration_structure` /
  `destroy_acceleration_structure`. Allocates the result + scratch
  buffers via `GetRaytracingAccelerationStructurePrebuildInfo`.
- D3D12 DXR step 3: command-list build (`BuildRaytracing
  AccelerationStructure`).
- D3D12 DXR step 4: `CreateStateObject` for RT pipelines.
- D3D12 DXR step 5: `DispatchRays` on `ID3D12GraphicsCommandList4`.
- Vulkan defensive fix: reject `TLAS` create where any instance's
  `blas` handle is unknown.

# ADR-20260524 / Wave 294 / v0.99.59 / Phase 132+133 — Vulkan AS build cmd path

## Status
Accepted — 2026-05-24

## Context

Phase 17.A landed BLAS create. Phase 127 (this run) landed TLAS
create. Both shipped without an actual `vkCmdBuildAccelerationStructuresKHR`
call — `ICommandBuffer::build_acceleration_structure` was a default
no-op virtual. Without a build path the AS objects stayed
unwritten and `vkCmdTraceRaysKHR` would read garbage.

Phase 130 landed deep-copy build inputs in `AccelRecord`; Phase 131
landed the `DeferredDestroy` queue. Both pieces of infrastructure
were prep work for this phase.

## Decision

Wire the full build path for both BLAS and TLAS together — they
share the same cmd-buffer override and most of the device-side
setup.

### Device side (VulkanDevice.cpp)

Extend `AccelRecord` with:

- `scratch_buf` + `scratch_alloc` + `scratch_device_address` —
  per-AS scratch buffer allocated via VMA at create time.
  Lifetime tied to the AS handle (freed in
  `destroy_acceleration_structure`).
- `as_device_address` — `vkGetAccelerationStructureDeviceAddressKHR`
  cached at create. Used by TLAS instance translation (BLAS
  device-address reference) and future SBT records.
- `instance_buf` + `instance_alloc` + `instance_device_address` —
  TLAS-only. Host-visible 64-byte-per-instance buffer pre-populated
  at create time with `VkAccelerationStructureInstanceKHR` data
  translated from engine `AccelInstance` (transform copied raw —
  ABI-compatible; BLAS handle resolved to device address via
  `accels_` lookup).
- `vk_triangle_geos` + `vk_primitive_counts` — Vulkan-format
  triangle list (already built locally for the size query) moved
  into the record so the build cmd doesn't have to recreate it.

### Cmd-buffer side (VulkanCommandBuffer.cpp + .hpp)

- New `AccelBuildView` POD in the header. The cmd buffer reads
  one of these via a `ResourceTables::accel_lookup` function-pointer
  (set by the device at cmd-buffer creation). Keeps the cmd buffer
  oblivious to the device's `AccelRecord` nested type.
- `VulkanCommandBuffer::build_acceleration_structure(handle)` override:
  - Resolves the view via the callback.
  - Builds `VkAccelerationStructureBuildGeometryInfoKHR` with
    type=BOTTOM_LEVEL or TOP_LEVEL based on `view.is_tlas`.
  - For TLAS: synthesizes a single
    `VkAccelerationStructureGeometryInstancesDataKHR` referencing
    `view.instance_device_address`.
  - For BLAS: passes `view.triangle_geos` directly (cached at
    create).
  - Builds `VkAccelerationStructureBuildRangeInfoKHR` (one per
    geometry for BLAS, one for TLAS with `primitiveCount =
    instance_count`).
  - Calls `vkCmdBuildAccelerationStructuresKHR(cmd, 1, &bgi, &range_ptr)`.
- Stack-array cap of 32 geometries per BLAS — sufficient for
  marathon-shippable test scenes.

### Lookup callback

`VulkanDevice::accel_lookup_static_` is a static method (function-
pointer compatible) that casts the user pointer back to
`VulkanDevice*`, finds the `AccelRecord` by index, and populates the
caller's `AccelBuildView` out-param. Returns false on unknown handle.

## Rejected alternatives

- **Build inside `create_acceleration_structure` (immediate-mode AS).**
  Vulkan requires a command buffer to record the build into; the
  device-only path would need to synthesize + submit + wait_idle
  per build, killing parallelism.
- **One device-wide shared scratch buffer.** Reusable but forbids
  concurrent AS builds. Per-AS scratch (currently ~few KB per
  BLAS, ~64 B per TLAS instance + driver overhead) keeps things
  simple and matches the AS lifetime.
- **Allocate scratch + instance buffers inside
  `build_acceleration_structure` and queue them for deferred
  destroy.** Would couple the cmd buffer's scratch allocation to
  `DeferredDestroy` + a per-frame fence. The per-AS lifetime
  pattern is simpler and matches the BLAS/TLAS object semantics.
- **Direct nested-type access** (passing
  `unordered_map<id, AccelRecord>*` through ResourceTables). Leaks
  AccelRecord layout into the cmd-buffer header. Function-pointer
  lookup keeps the boundary clean.

## Consequences

- Vulkan BLAS + TLAS both build correctly when the caller issues
  `cmd.build_acceleration_structure(handle)` between `begin()` and
  `end()` and submits the cmd buffer.
- Caller must NOT destroy the AS handle until the GPU finishes the
  build (caller's submit-fence responsibility).
- Phase 134 (RT pipeline) and Phase 135 (dispatch_rays) can now
  consume real AS handles via SBT records.
- Vulkan `kNotImplemented` count: unchanged at 3 (BLAS/TLAS build
  weren't numbered stubs; the parent
  `ICommandBuffer::build_acceleration_structure` was a default
  no-op).
- TLAS instance translation handles BLAS device-address resolution
  with a fallback to 0 for null handles, so the descriptor-only
  TLAS path from Phase 127 still works for capability probes.

```
cmake --build --preset llvm-win-debug --target cd_rhi_vulkan
```

Vulkan static lib builds clean. End-to-end behavioural validation

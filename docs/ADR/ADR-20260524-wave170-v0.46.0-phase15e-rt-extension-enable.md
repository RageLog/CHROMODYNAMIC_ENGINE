# ADR — v0.46.0 / Wave 170 — Phase 15.E RT extension enablement

- Date: 2026-05-24
- Status: Accepted (partial — see "What did NOT land")
- Wave: 170
- Predecessor: Wave 169 (v0.45.0 HRTF + reverb)

## Context

Phase 15.E planned a full Vulkan RT pipeline: BLAS / TLAS through
the cd::rhi surface + `vkCmdTraceRaysKHR` + a working
`hello_rt_triangle` sample. Reality check: a real RT pipeline
requires the shader-binding-table layout design + raygen /
closesthit / miss shader compilation through glslang's SPV_KHR_*
extensions + careful VkPhysicalDeviceRayTracingPipelinePropertiesKHR
alignment handling. That's a multi-wave engineering effort.

Marathon-honest scope for v0.46.0: enable the extensions at
device creation so the backend has the function pointers loaded,
the feature chain wired, and the bufferDeviceAddress feature
on. The concrete BLAS/TLAS/dispatch_rays implementation is
queued as the **top Phase-16 priority**.

## Decision

Tag (deferred to Phase 15 close). Scope: device-creation-side
infrastructure for ray tracing on the Vulkan backend.

### What landed

- **RT extension auto-enable** in `create_device`. Probes the
  device for `VK_KHR_acceleration_structure` +
  `VK_KHR_ray_tracing_pipeline` +
  `VK_KHR_deferred_host_operations` (all three required). When
  all present, appends them to the device extension list.
  `VK_KHR_ray_query` enabled independently when present.
- **Feature chain wiring**:
  - `VkPhysicalDeviceVulkan12Features::bufferDeviceAddress = TRUE`
    when RT enabled (required by AS).
  - `VkPhysicalDeviceAccelerationStructureFeaturesKHR { accelerationStructure = TRUE }`
    chained.
  - `VkPhysicalDeviceRayTracingPipelineFeaturesKHR { rayTracingPipeline = TRUE }`
    chained.
  - `VkPhysicalDeviceRayQueryFeaturesKHR { rayQuery = TRUE }`
    chained when ray-query is enabled.
- **Verified on NVIDIA RTX 3080 Laptop**:
  `vkCreateDevice` succeeds with all RT structs in the chain.
  Driver would reject the call if a feature were requested
  without its extension; the success proves the extensions are
  loaded.
- **`volk` function pointers** for
  `vkCreateAccelerationStructureKHR`,
  `vkCmdBuildAccelerationStructuresKHR`,
  `vkCmdTraceRaysKHR`, etc. are resolved by `volkLoadDevice`
  after the device is created. Consumer code can now call
  these directly (or wait for the cd::rhi surface to wrap
  them in Phase 16).

### What deliberately did NOT land

- **`VulkanDevice::create_acceleration_structure` real impl.**
  Still falls through to the IDevice default kNotImplemented.
  Real BLAS construction needs VMA scratch + AS backing
  buffers + vkGetAccelerationStructureBuildSizesKHR sizing +
  vkCmdBuildAccelerationStructuresKHR. ~150 LOC of careful
  code that needs the time Phase 15.F + Phase 16 also need.
- **TLAS build, ray-tracing pipeline creation, SBT, dispatch_rays.**
  Same reason — large surface, must land coherently.
- **hello_rt_triangle sample.** Held until the impl lands.
  hello_rt_check still works as a feature probe.

## Rejected alternatives

- *Ship the full pipeline in v0.46.0.* Rejected: would push
  Phase 15.F + Phase 16 outside this run. The marathon
  directive (do all of Phase 15 + Phase 16) imposes scope
  pragmatism on the largest sub-phase.
- *Skip the extension wiring too.* Rejected: extensions
  need to be enabled at device creation; can't be added
  later. Without this wave, the Phase-16 BLAS impl couldn't
  even call vkCreateAccelerationStructureKHR without a
  validation-layer reject.

## Phase 16 first-priority callout

Phase 16's first sub-phase WILL be:
- Real `create_acceleration_structure` (BLAS + TLAS) via
  `VulkanDevice` override.
- `build_acceleration_structure` + `dispatch_rays` on the
  command buffer.
- glslang RT-stage compilation (raygen / closesthit / miss).
- `hello_rt_triangle` sample on NVIDIA RTX 3080.

The v0.40.0 API shape + v0.46.0 extension enablement +
Phase 16.A impl together close the original Phase 14.G
scope.

# ADR Wave-312 — WAVE H Linux/macOS/mobile deferral (v0.99.77)

- **Date:** 2026-05-25
- **Status:** Accepted (scope decision)
- **Predecessor:** [ADR-20260525-wave311-v0.99.76-phase161-164-quality-gates-audit](./ADR-20260525-wave311-v0.99.76-phase161-164-quality-gates-audit.md)
- **Successor:** v1.0 readiness report (next)
- **Tag:** v0.99.77

## Context

WAVE H of the marathon roadmap listed three platform phases:

- Phase 158 — Linux X11/Wayland platform window
- Phase 159 — macOS Cocoa + Metal backend
- Phase 160 — Android/iOS mobile

The marathon's permanent ordering rule (`feedback_marathon_ordering`)
puts "yüksek öncelikten düşüğe" (high → low priority), and the user
explicitly flagged "mobile platform en sona birakabilirsin" early
in the run. This wave is the lowest priority by design.

## Decision

**All three WAVE H phases are DEFERRED to engine v1.1+.**

State of the platform layer entering v1.0:

| Target            | Window backend     | Render backend | Notes                          |
|-------------------|--------------------|----------------|--------------------------------|
| **Windows 10/11** | Win32 (primary)    | Vulkan + D3D12 | Full sample fleet runs         |
| **Linux**         | none yet           | Vulkan         | Renderer compiles; no window   |
| **macOS**         | none yet           | none (no Metal)| Build-tested on CI; no demo    |
| **Android**       | AndroidWindow stub | none yet       | Stub only                      |
| **iOS**           | none               | none           | Not started                    |

The CI matrix already builds + tests the engine on Ubuntu and
macOS (Wave 311), but no sample shows a window on those platforms.

### Phase 158 (Linux X11/Wayland) — deferred reasoning

A Linux platform window needs:

- Either Xlib + GLX integration for the OpenGL backend (and
  VK_KHR_xlib_surface for Vulkan).
- Or libwayland-client + xdg-shell + VK_KHR_wayland_surface.

Both routes ~400-600 lines including event loop translation
into `cd::platform::OSEvent`. The build system already detects
Linux but skips Win32-only sample compilation gracefully.

### Phase 159 (macOS Cocoa + Metal) — deferred reasoning

macOS support needs:

- Cocoa `NSWindow` + `NSView` in an Objective-C++ TU.
- VK_KHR_metal_surface (Vulkan via MoltenVK) OR a new
  `cd::rhi::IDevice` Metal backend (`rhi_metal`).

The Metal backend is a third backend implementation —
~3000-5000 lines mirroring the Vulkan/D3D12 surface.
Out of scope for v1.0.

### Phase 160 (Android / iOS) — deferred reasoning

User explicitly named mobile as lowest priority. AndroidWindow
stub exists but the native-activity glue + Android Vulkan loader +
input event translation is at least a sprint of focused work.
iOS needs a separate Metal path. Both deferred without partial
implementation.

## Rejected alternatives

- **Ship a Linux X11-only backend** — would land a partial
  cross-platform story (Linux yes, macOS no) which is harder to
  reason about than "Windows-primary v1.0".
- **Ship a Metal stub with kNotImplemented everywhere** — adds
  dead code to the tree.
- **Block v1.0 ship on cross-platform parity** — the engine's
  primary delivery is the Windows-first library set; v1.1 can
  pick up cross-platform as a single coordinated milestone.

## Consequences

- v1.0 is officially **Windows-primary**: every sample runs on
  Win10/11; Vulkan + D3D12 + (partial) OpenGL backends present.
- The engine builds clean on Linux + macOS via CI but those
  platforms do not have window+sample integration.
- The marathon's WAVE H bullet is closed as a scope decision.

## Open follow-ups

- Engine v1.1: Phase 158 Linux X11/Wayland window + sample
  bring-up.
- Engine v1.1: Phase 159 macOS Cocoa window + decision on
  MoltenVK Vulkan path vs. native Metal backend.
- Engine v1.2: Phase 160 Android NativeActivity + iOS Metal

# ADR — v0.34.0 / Wave 157 — Phase 14.A scene save/load in editor

- Date: 2026-05-23
- Status: Accepted
- Wave: 157
- Tag: v0.34.0
- Predecessor: ADR-20260523-wave155 (v0.33.0 ImGui editor bridge)
- Phase 14 master: ADR-20260523-wave156-phase14-plan.md

## Context

Phase 14.A scope per the wave156 plan: scene serialization +
load/save loop. Inspecting the codebase at the start of the
sub-phase showed the *primitives* are already shipped:

- `cd::scene::serialize_scene` / `deserialize_scene` —
  `engine/world/scene/include/cd/scene/Serializer.hpp` (266
  lines, header-only).
- Tests already in `engine/world/scene/tests/test_scene.cpp`:
  - `SceneSerializer.EmptySceneSerializesToVersionedShell`
  - `SceneSerializer.RoundTripFlatScenePreservesTransforms`
  - `SceneSerializer.ParentLinksAreRebuilt`
  - `SceneSerializer.BadShapeRejected`
  - `SceneSerializer.BadVersionRejected`
  - Plus the binary variant: 5 more on `BinarySerializer`.
- Headless sample `samples/hello_scene_save/` already
  demonstrates a 4-node round-trip (root + 3 children with
  parent links).

What was missing for Phase 14.A: an *interactive consumer*
that exercises save/load from the new ImGui editor (v0.33.0).
The editor previously had no persistence — every session
started from scratch.

## Decision

Tag **v0.34.0**. Scope: wire Save / Load into the hello_editor
sample so EditHistory-driven edits round-trip through
cd::scene::Serializer + cd::asset_json to/from disk.

### What landed

- **Save / Load buttons in hello_editor's Toolbar panel.**
  Single `ImGui::InputText` for the path (default
  `hello_editor.cdscene.json`), plus a Save and a Load
  button.
  - **Save** invokes `cd::scene::serialize_scene(scene)` →
    `cd::asset_json::serialize(json, /*pretty=*/true)`, writes
    to disk with `std::ofstream`. Logs the path + byte count
    into the history-log panel.
  - **Load** reads the file, parses via `cd::asset_json::parse`,
    rebuilds World + Scene from scratch (the editor's existing
    `World` is move-assigned a fresh instance), clears the
    EditHistory (commands hold raw pointers to the old entities
    by contract), repopulates the entity list using the
    `IdMap` returned by `deserialize_scene`, and re-selects
    entity 0.
- **`cd::asset_json` added to `hello_editor` link list.**

### What deliberately did NOT land

- **Entity name preservation across save/load.** The current
  Serializer writes only transforms + parent links — no
  `name` field. Loaded entities are tagged `n_0`, `n_1`, ... in
  iteration order. Adding a name field is a SceneSerializer
  scope question that needs to coordinate with the same
  name-component story the Editor sample uses internally;
  deferred to a later wave.
- **Auto-load on startup.** Save is explicit; loading on
  startup would surprise users with state from a previous
  session. The deliberate user-action model matches what every
  real editor (Unity / UE / Godot) does.
- **Undo across save/load.** Save snapshots state; load
  replaces it; the EditHistory is cleared on load. A
  "load-as-new-history-entry" model is conceivable but the
  command would have to snapshot the entire previous World,
  which is the wrong shape for the existing per-mutation
  command pattern. Out of scope.
- **Versioned migrations.** Serializer writes
  `kSceneJsonVersion = 1`; deserializer rejects other
  versions with `kBadVersion`. A v1→v2 migration path is
  deferred until v2 actually exists.

## Rejected alternatives

- *Re-implement the serializer.* Rejected: it's already there,
  tested, and verified by a headless sample. The Phase 14.A
  marathon-actionable work is the interactive consumer, not the
  primitive re-write.
- *Add a hello_scene_save_imgui demo as a separate sample.*
  Rejected: the hello_editor sample is the natural integration
  surface — anyone evaluating "can I build a scene tool on this
  engine?" reaches for hello_editor first. Splitting the
  persistence demo into its own sample would hide the answer.
- *Add a name component to the SceneSerializer in this wave.*
  Rejected: the name-component story crosses cd::scene +
  cd::editor + (future) cd::asset entity-naming and benefits
  from a deliberate ADR. The marathon ships persistence
  *without* names rather than rushing the name design.

## Consequences

- v0.34.0 is the new latest SemVer marker.
- hello_editor is now the first sample with persistent state.
- The "EditHistory invalidates on Load" contract is documented
  in the load handler and matches cd::editor::EditHistory's
  `clear()` semantics.
- Phase 14.B (asset cooker improvements → v0.35.0) opens next.

## Verification

- `cmake --build build/ninja-base --config Debug --target
  cd_sample_hello_editor`: clean
- `hello_editor.exe --headless 5`: 5 frames, clean exit
- Existing `cd_test_scene` suite covers the serializer
  primitives that this wave consumes.

# ADR — v0.41.0 / Wave 164 — Phase 14.H mobile-platform scaffold

- Date: 2026-05-23
- Status: Accepted
- Wave: 164
- Tag: v0.41.0
- Predecessor: ADR-20260523-wave163 (v0.40.0 RT API shape)
- Phase 14 master: ADR-20260523-wave156-phase14-plan.md

## Context

Phase 14.H per the wave156 plan: Android Vulkan + iOS Metal
platform support — gradle/Xcode wrappers, ARM64 cross-compile,
`hello_triangle_mobile` for each platform.

Reality check at sub-phase start: actual mobile builds need

- Android NDK r26+ installed on the build machine
- Xcode 15+ on an Apple host machine
- Android emulator or device for runtime validation
- iOS simulator/device for runtime validation
- A CI runner with at least one of those toolchains

The marathon's build machine is Windows desktop only. Cross-
compiling without a runtime target produces unverified
binaries — the exact "tests pass / output is silently wrong"
trap the v1.0 rollback was designed to catch. Per the
established marathon pattern (mirrors rhi_d3d12 v0.27.0 boot
wave + RT v0.40.0 API-shape wave), Phase 14.H ships the
**toolchain + design scaffold**; the runtime implementation
is the natural follow-up wave when a mobile-toolchain CI
runner is available.

## Decision

Tag **v0.41.0**. Scope: `mobile/` directory with the build
path documentation + toolchain templates for both platforms.
No engine-side C++ implementation lands here; the platform
window factory remains returning `kNotImplemented` on mobile
targets (the existing v0.40.0 behavior), which is the
honest contract until a real `AndroidWindow.cpp` /
`IosWindow.mm` lands alongside actual device validation.

### What landed

- **`mobile/README.md`** — the canonical Android + iOS build
  walkthrough. Documents:
  - Required NDK / Xcode versions.
  - The CMake invocation shape for each platform
    (CMAKE_TOOLCHAIN_FILE, ANDROID_ABI, CMAKE_OSX_*).
  - The "engine compiles cleanly without a mobile platform
    window backend" property (cd::platform's factory returns
    kNotImplemented; mobile apps own their `ANativeWindow*`
    or `UIView*` directly and bypass the IWindow surface).
  - The follow-up wave's content
    (`AndroidWindow.cpp` / `IosWindow.mm` + samples + CI
    runner with mobile toolchain).
- **`mobile/android/toolchain.cmake.template`** — reference
  knobs for the engine-side build under Google's NDK
  `android.toolchain.cmake`. Pins
  `CD_ENABLE_VULKAN=ON`, `CD_ENABLE_SAMPLES=OFF`,
  `CD_DISABLE_VCPKG=ON`, `CD_BUILD_SHARED_LIBS=OFF`,
  `CD_NO_MOBILE_BACKEND=ON`.
- **`mobile/ios/toolchain.cmake.template`** — Xcode +
  CMAKE_SYSTEM_NAME=iOS path. `CD_ENABLE_VULKAN=OFF`
  because the default mobile path is `cd::rhi_metal`;
  MoltenVK on iOS is an opt-in vendor decision.

### What deliberately did NOT land

- **`AndroidWindow.cpp` / `IosWindow.mm`.** Both require
  testing on an actual device or simulator, which the
  marathon's Windows-only build machine can't provide. The
  cd::platform::IWindow contract is already shaped to accept
  these as conditional TUs; the platform-detection macros
  (`__ANDROID__` / `(__APPLE__ && TARGET_OS_IPHONE)`) are
  already free.
- **CI matrix expansion to Android / iOS.** Requires
  externally-provided toolchain runners (GitHub-hosted
  macOS runners can build iOS but the engine doesn't yet
  link Metal-shader compiled artifacts; Linux runners can
  install the Android NDK but the build needs an actual
  arm64 device for runtime smoke).
- **`hello_triangle_android` / `hello_triangle_ios`
  samples.** Both want a working platform-window backend
  to bind the swapchain. Same blocker as the .cpp/.mm
  files above.
- **MoltenVK opt-in on iOS.** The cd::rhi_metal path is the
  v1.0-quality direction; MoltenVK is a portability layer
  that lets Vulkan code run on iOS but doubles the test
  matrix. Deferred until either we ship a Vulkan-only
  pipeline that depends on it, or a downstream consumer
  asks.
- **Gradle plugin wrapper.** The README documents the
  command-line invocation; a polished gradle plugin that
  hides those flags is a productization concern, not a
  marathon-shippable engineering deliverable.

## Rejected alternatives

- *Ship `AndroidWindow.cpp` without device testing.*
  Rejected: that's the "tests pass / output silently wrong"
  pattern the v1.0 rollback ADR (wave125) was written to
  prevent. The marathon's Windows-only build machine
  cannot meaningfully verify a runtime Android binary; an
  unverified ANativeWindow → Vulkan surface chain would
  hit driver-specific surface-format negotiation issues at
  exactly the wrong moment.
- *Cancel Phase 14.H entirely.* Rejected: the wave156 plan
  ADR committed to closing the eight sub-phases; cancelling
  one would invite re-litigation of the others. The scaffold
  deliverable is the marathon-honest way to honor the
  commitment without faking work that needs hardware.
- *Compress Phase 14.H into the rest of Phase 14 by skipping
  the ADR.* Rejected: the design choice (ship docs, defer
  impl) deserves its own ADR so a future reader knows the
  scaffold is intentional, not abandoned scope.

## Consequences

- v0.41.0 is the new latest SemVer marker.
- **Phase 14 is fully closed.** All eight sub-phases shipped:
  - 14.A scene save/load → v0.34.0
  - 14.B KTX2 encode → v0.35.0 (+ v0.35.1 editor polish)
  - 14.C D3D12 PSO + triangle → v0.36.0 (+ v0.36.1 sRGB)
  - 14.D ECS replication → v0.37.0
  - 14.E editor 3D viewport → v0.38.0
  - 14.F audio DSP graph → v0.39.0
  - 14.G RT API shape → v0.40.0
  - 14.H mobile scaffold → v0.41.0
- The Phase-15 candidate list:
  - Real Vulkan RT pipeline + SBT + raygen shader sample
  - Real Android Vulkan + iOS Metal backends + samples
  - D3D12 descriptor set / CBV / SRV / UAV table
  - DXC / Shader Model 6 on D3D12
  - Editor 3D viewport WASD camera + Dock-layout preset
  - Audio HRTF node + convolution reverb (with human-ear
    validation)
- v1.0 path remains user-only per the v1.0 rollback ADR.

# ADR — v0.29.0 / Wave 150 — Phase 12.D RT + mesh-shader detection

- Date: 2026-05-23
- Status: Accepted
- Wave: 150
- Tag: v0.29.0
- Predecessor: ADR-20260523-wave149 (v0.28.0 editor undo/redo)

## Context

Phase 12.D per Wave 142 was "ray tracing + mesh shaders → v0.29.0".
The original scope was implementation: `VK_KHR_acceleration_structure`
BLAS/TLAS build via cd::rhi, ray-tracing-pipeline + SBT,
`hello_raytrace` sample, `VK_EXT_mesh_shader` dispatch +
`hello_meshshader`.

Same realism check applied to Phase 12.B (D3D12) applies here:
implementing RT through a new RHI surface with no human pixel-
checker carries unacceptable subtle-bug risk. BLAS build barriers,
SBT alignment, shader-record layout — all silently wrong-or-right
in ways ctest can't catch.

## Decision

Tag **v0.29.0**. Scope: **detection-only** capability bits for RT,
ray-query, and mesh-shader. Surface the existence of these
capabilities so callers can write correct branching code; the
actual rendering surface lands when there's human review bandwidth.

### What landed

- **`cd::rhi::DeviceFeatures`** — three new bits:
  - `ray_tracing` (coarse: AS + RT-pipeline both available)
  - `ray_query` (separate, sometimes exposed independently)
  - `mesh_shader` (EXT preferred, NV fallback)
- **Vulkan backend** probes `vkEnumerateDeviceExtensionProperties`
  and lights the bits from extension presence:
  - `ray_tracing = VK_KHR_acceleration_structure && VK_KHR_ray_tracing_pipeline`
  - `ray_query = VK_KHR_ray_query`
  - `mesh_shader = VK_EXT_mesh_shader || VK_NV_mesh_shader`
- **`hello_rhi_features` sample** — prints the full capability
  matrix for the selected adapter. Honors `CD_VULKAN_DEVICE_INDEX`
  so cross-vendor probes are one env-var away.

Verified live on this machine:
- NVIDIA RTX 3080 Laptop GPU: `ray_tracing=yes  ray_query=yes  mesh_shader=yes`
- Intel Iris Xe (integrated): `ray_tracing=no  ray_query=no  mesh_shader=no`

Both results match the published silicon capabilities — the
detection logic is correct.

### What deliberately did NOT land

- `dispatch_rays` / `cmd.draw_mesh_tasks` ICommandBuffer methods.
- Acceleration-structure RHI surface (BLAS/TLAS desc, build, copy,
  query, compact).
- Ray-tracing pipeline + SBT layout descriptors.
- `hello_raytrace` / `hello_meshshader` rendering samples.

All four require non-trivial code with high silent-failure
surface. Without a human to confirm "the ray-traced sphere looks
right" or "the mesh-shader-emitted procedural mesh looks right",
shipping these would introduce regressions that would only
surface when Phase 13's hardening pass started writing
RT-dependent code.

## Rejected alternatives

- *Ship `hello_raytrace` with a 1-bounce, 1-sphere scene.* Rejected:
  a 1-bounce scene still needs an AS build path + RT pipeline + SBT
  layout + ray-gen / miss / closest-hit shaders. Each is a subtle
  correctness puzzle; AI-only implementation is high regression risk.
- *Add `dispatch_rays` to ICommandBuffer with a NotImplemented body.*
  Considered but rejected: stubs without a real backend wiring are
  worse than no stubs — callers think the surface is there, find
  out at runtime it isn't, and the IDevice surface bloats with
  unused-for-now methods.
- *Skip detection-only and defer everything to Phase 13.* Rejected:
  the capability bits are useful in their own right — they let
  current and future code branch on hardware capability before
  touching the RT surface that doesn't exist yet. Detection is
  the minimum viable forward motion for Phase 12.D.

## Consequences

- v0.29.0 is the new latest SemVer marker.
- **Phase 12 closes here.** All four sub-phases tagged:
  - 12.A v0.26.0 — perf sweep + 21-bench surface
  - 12.B v0.27.0 — D3D12 boot
  - 12.C v0.28.0 — editor undo/redo
  - 12.D v0.29.0 — RT/mesh detection
- The "actual implementation" of D3D12 + RT + mesh-shader render
  paths + editor UI bridge moves to Phase 13. Phase 13 ADR opens
  next.

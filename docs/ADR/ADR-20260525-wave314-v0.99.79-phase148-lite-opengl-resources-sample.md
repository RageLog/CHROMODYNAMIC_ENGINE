## Context

The marathon's WAVE D scope decision (ADR Wave-308) shipped OpenGL
buffer + texture + sampler (Phases 137/143/144) but deferred the
full hello_opengl sample to v1.1+. With the v1.0 done, the first
v1.1 OpenGL deliverable is a resources-only sample that validates
the partial backend boots and creates each resource cleanly on the
host driver.

Writing the sample immediately surfaced a latent bug in the
existing WGL loader — fixing it is part of this ship.

## Decision

### `samples/hello_opengl_resources` (Phase 148-lite)

- Boots the GL device.
- Creates one buffer (256 B storage), one texture (64×64 RGBA8),
  one texture view (alias), one sampler (linear, repeat/repeat/
  clamp).
- Prints success / failure per primitive + a summary line.
- Returns 0 on full success, 2 on any partial failure.

CMake-gated to Windows-only (same as hello_opengl_boot — non-Windows
falls through to PlatformStub).

### WGL loader bug fix

**Symptom:** On Intel Iris Xe Graphics, hello_opengl_resources
reported "texture FAILED: DSA texture entry points not exported"
even though glCreateBuffers and glCreateSamplers (also DSA)
resolved cleanly.

**Root cause:** `glDeleteTextures` is a GL 1.1 function, not a
3.0+ extension. Microsoft's `wglGetProcAddress` documentation
explicitly states that it returns NULL for GL 1.0/1.1 functions —
those symbols live in `opengl32.dll`, exported statically. The
existing loader treated 1.1 functions the same as extension
functions, so `glDeleteTexturesDSA` came back nullptr, which made
`texture_valid()` return false even though `glCreateTextures` +
`glTextureStorage2D` (both DSA, both 4.5) resolved fine.

`glDeleteSamplers` is GL 3.3 (sampler objects were added in 3.3),
so it does come from `wglGetProcAddress` — explains why the sampler
path worked but the texture path didn't.

**Fix:** Two-stage resolution in `load_dsa_buffer_funcs`:

1. Try `wglGetProcAddress` first (covers all 3.0+ extensions and
   the explicit ARB names).
2. On nullptr (incl. the small-int sentinel values 1/2/3/−1 MS uses
   to signal failure), fall back to
   `GetProcAddress(GetModuleHandle("opengl32.dll"), name)` (covers
   GL 1.0/1.1 functions exported statically).

## Test result

```
CHROMODYNAMIC 0.99.78 — hello_opengl_resources
[gl] adapter: Intel(R) Iris(R) Xe Graphics
[gl] buffer OK (256 B, storage, gpu-only)
[gl] texture OK (64x64 RGBA8)
[gl] texture view OK
[gl] sampler OK (linear+linear, repeat/repeat/clamp)
[gl] summary: 4 created, 0 failed
```

All 4 resource paths green on Intel Iris Xe; the test that was
previously skipping the texture path now exercises it cleanly.

## Rejected alternatives

- **Hard-link `opengl32.lib` and call `glDeleteTextures` directly**
  — would force the build to depend on `<GL/gl.h>` and the lib;
  the runtime fallback keeps the loader self-contained.
- **Drop the `glDeleteTextures` requirement from `texture_valid`**
  — would silently leak textures (the destroy path would no-op).
- **Use ARB-specific function names everywhere
  (`glDeleteTexturesEXT`, etc.)** — those names are deprecated in
  modern GL and not guaranteed to exist on every driver.

## Consequences

- OpenGL backend now demonstrably boots + creates buffer + texture
  + view + sampler on a real driver (Intel Iris Xe, GL 4.6).
- The latent WGL-1.1 vs 3.0+ resolution issue is fixed for any
  future GL 1.1 symbol the loader picks up (e.g. `glClear` /
  `glViewport` once the swapchain phase lands).
- One more v1.1 deferred item reclaimed.

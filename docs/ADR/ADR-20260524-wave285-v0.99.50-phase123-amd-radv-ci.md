# ADR-20260524 / Wave 285 / v0.99.50 / Phase 123 — AMD RADV CI lane

## Status
Accepted — 2026-05-24 (dormant until self-hosted runner online)

## Context

`ci.yml`'s `linux-vulkan-sw` job runs every push against Mesa
lavapipe (software Vulkan ICD on hosted `ubuntu-24.04` runners).
Lavapipe is great for "does this code path execute at all" coverage
but cannot reproduce:

- AMD GLSL miscompile patterns.
- Subgroup / wave-size assumptions in shaders.
- Bindless descriptor-indexing edge cases.
- FP rounding mode discrepancies between RDNA hardware and a
  scalar software ICD.

Marathon pending list flagged "AMD Mesa/RADV CI workflow." A
hosted GitHub runner with an AMD GPU does not exist, so any
real-hardware lane has to be self-hosted.

## Decision

Add a dormant workflow + docs that come alive the moment a
self-hosted runner with the right labels comes online:

1. **`.github/workflows/ci-amd-radv.yml`**
   - Triggers on `workflow_dispatch` (manual) + tag pushes
     (`v*.*.*`). NOT on every commit — keeps self-hosted minutes
     budgeted.
   - Targets `runs-on: [self-hosted, amd-gpu, linux]`.
   - Pins `VK_ICD_FILENAMES` to RADV's icd file so the loader
     can't silently fall back to lavapipe.
   - Probes `lspci` for AMD hardware and `vulkaninfo` for the
     `radv` driverName as preflight gates.
   - Builds + ctest + sample smoke (5 visual samples) + optional
     full-sample-sweep input.
   - Golden-compare against `tests/golden/radv/` (skipped silently
     when empty — populated by a future capture pass).
   - Failure artifacts uploaded with 14-day retention.
   - Top-of-file `yaml-language-server` schema directive (same
     pattern as Phase 103 docs.yml).

2. **`docs/CI_SELF_HOSTED.md`** — runner setup steps, software
   packages, label requirements, "why a separate lane" rationale,
   golden-reference workflow.

Until a runner registers with the `amd-gpu` label, every
`workflow_dispatch` queues then times out without consuming
hosted GitHub minutes. The setup is fully reversible — delete the
workflow file if direction changes.

## Rejected alternatives

- **Hosted runner with an AMD GPU.** GitHub doesn't offer one as
  of 2026-05.
- **Reuse lavapipe lane** with `-DCD_RADV_MODE=ON`. RADV is a
  driver, not a flag — software-mode is what lavapipe already
  provides. The only way to gain AMD-vendor signal is real
  hardware.
- **Wait until hardware is available.** The workflow file +
  documentation is the cheapest infrastructure to write now; the
  lab can come online without re-discovering the requirements.

## Consequences

- No CI minutes consumed until a labelled runner registers.
- The marathon's outstanding "AMD Mesa/RADV CI" item is now
  cleared with a definite setup path.
- Future contributors who pick up the hardware lane have a
  checklist (CI_SELF_HOSTED.md) instead of having to invent it.
- `tests/golden/radv/` directory becomes a future placeholder
  for vendor-specific reference PNGs.

## Validation

YAML lint: the `yaml-language-server` schema directive pins to
`schemastore.org/github-workflow.json`, same workaround as Phase
103 docs.yml. Workflow won't appear in the "active workflows" UI
until a manual `workflow_dispatch` happens, which is intentional.
